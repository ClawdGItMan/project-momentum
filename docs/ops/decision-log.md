| 2026-03-16 | Use friend invites and mutual acceptance instead of a follower model in v0.1. | Friends are simpler and more intuitive for the first release, while followers can be explored in a later version if needed. | Max | Revisit once v0.1 usage shows whether a broader social graph is needed. |
| 2026-03-16 | Aim for a premium-fitness visual direction with restrained color and a few meaningful animations. | The app should feel high-quality and desirable without drifting into luxury branding or noisy gamified UI. | Max | Revisit if early design explorations feel too sterile, too flat, or too intense. |
| 2026-03-16 | Increase the target squad size range to 3–15 people. | Larger squads can still feel intimate while fitting more realistic friend-group and community use cases. | Max | Revisit if feed quality or reciprocity breaks down in larger groups. |
| 2026-03-16 | Make the integration architecture adapter-friendly from day one, with Apple Health prioritized and Strava next in line. | The product should be easy to extend across health data sources without forcing multiple costly live integrations in the first sprint. | Max | Revisit if the sprint proves a second live provider is essential for conviction. |
| 2026-03-16 | Upgrade the repo to a build-first multi-agent framework with explicit design, frontend, backend/integrations, and QA roles. | The previous framework was strong on research and planning but underpowered for actually shipping a high-quality app. | Max | Revisit if the role system becomes too heavy or redundant for the team. |
| 2026-03-16 | Make workouts and habits the default friend-visible categories in v0.1. | These are the safest, clearest social signals to share by default while other categories remain selectively shared. | Max | Revisit if early users want a different privacy baseline. |
| 2026-03-16 | Use consistency as a first-class metric tied to check-ins and habit completion, including workouts. | The product needs a clear signal that someone is actively showing up, not just logging isolated actions. | Max | Revisit once the exact calculation and visualization have been tested in the prototype. |
| 2026-03-16 | Treat Apple Health as a required v0.1 integration, with manual entry only as fallback. | Real health connectivity is core to the credibility of the first product experience. | Max | Revisit only if a hard technical blocker threatens the sprint. |
| 2026-03-16 | Use an Expo custom iOS development-build workflow with prebuild instead of optimizing around Expo Go. | Apple Health requires native configuration and HealthKit capability setup, so a development build is the fastest credible path. | Max | Revisit only if the native setup meaningfully slows iteration more than it helps prototype credibility. |
| 2026-03-16 | Define consistency v0 as a 7-day score plus label with 40% check-ins, 40% habits, and 20% workouts. | The prototype needed an implementation-ready model that could appear across onboarding, profile, habits, and feed without reopening scoring debates. | Max | Revisit after user testing shows whether the score feels motivating or overly clinical. |
| 2026-03-16 | Make the first build slice onboarding -> Apple Health -> skippable squad step -> first workout check-in -> seeded Home. | This is the smallest slice that proves identity, selective sharing, real-data posture, and social payoff in one session. | Max | Revisit if demos show that another destination communicates the product better than Home. |
| 2026-03-16 | Keep squad selection as a suggested, skippable onboarding step. | Squads need to stay central without creating enough onboarding friction to block the first successful check-in. | Max | Revisit if early users skip squads so often that the accountability model weakens. |
| 2026-03-16 | Persist non-sensitive demo session state across reloads, but do not persist raw Apple Health snapshots. | The prototype needed repeatable demos without turning local storage into a broader health-data cache. | Max | Revisit if live demos require offline metric persistence or stronger encrypted local storage. |
| 2026-03-16 | Narrow HealthKit consent to the read-only MVP bundle and remove unused Health write messaging. | The current v0.1 product only needs workout, steps, sleep, and active-energy reads, so broader write consent would overstate the privacy surface. | Max | Revisit when the product adds a real HealthKit write path. |
| 2026-03-16 | Add dev-only demo controls plus a dedicated demo runbook and EAS profiles. | The team needs a repeatable way to stage connected, preview, fallback, and reset flows across browser, Xcode, and EAS contexts without changing the core product. | Max | Revisit if the controls start leaking into the real product experience or demo needs stabilize. |
